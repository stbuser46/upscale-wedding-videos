# Chapter-based restoration web UI specification

Status: implementation plan for the next phase.

## Product goal

Provide a private web interface that catalogs the two wedding DVDs, shows their
titles and chapters visually, and lets the user restore only the important
sections.

The UI must support both DVD-defined chapters and arbitrary time slices. It
must also operate long GPU jobs safely: queue, prioritize, start, request a
pause, resume after a pause or restart, cancel, inspect progress and logs, and
download completed results.

The project will not automatically restore an entire disc. The intended flow
is inspect, prioritize, restore selected sections, review, then decide what is
worth processing next.

## Existing UI

`webui/` currently contains a Flask application on port 8092 for blind image
and video comparisons. It reads a manifest and appends votes to a JSONL file.
It has useful small pieces such as HTTP Range file serving, but it is explicitly
disposable, has no authentication, no database, and does not manage jobs.

The chapter/job UI should be a new application mode rather than quietly
turning the voting manifest into a process manager. Historical voting data and
assets must remain readable.

## User workflow

### 1. Scan discs

The application scans `source/weddind_dvd_1.ISO` and
`source/weddind_dvd_2.ISO` read-only.

It discovers:

- DVD identity/label;
- titles and title durations;
- chapter number, start, end and duration;
- angles or alternate program chains when present;
- video/audio/subtitle stream metadata;
- likely duplicate, menu or very short titles.

Chapter data must come from ISO/IFO navigation metadata, preferably through
`libdvdread`/`lsdvd`, not by guessing scene cuts in an extracted VOB.

The scanner stores raw discovery output for auditing and a normalized chapter
catalog in the application database.

### 2. Generate review media

For each useful title/chapter, create lightweight browser-compatible review
assets without AI:

- one representative thumbnail;
- an optional contact strip containing several evenly spaced frames;
- an H.264/AAC proxy for browser playback;
- a waveform or simple audio-presence indicator if useful.

Proxy generation is a separate, inexpensive job type. It must not be confused
with an archival restoration.

### 3. Prioritize chapters

The library screen presents each DVD as titles containing chapters. The user
can:

- play a chapter proxy;
- rename a title or chapter without modifying the ISO;
- mark `high`, `normal`, `low`, or `skip` priority;
- add notes such as “ceremony”, “speeches” or “poor exposure”;
- select several chapters and add them to the restoration queue;
- reorder queued work.

### 4. Select a custom time slice

The title player includes a timeline and in/out controls. A user can enter or
drag:

- start time;
- end time or duration;
- an optional output name and note;
- priority.

Times are stored relative to a DVD title, not only relative to a generated VOB.
The UI displays both title timecode and absolute seconds used by the worker.

Validation rules:

- start must be at or after zero;
- end must be after start and inside the selected title;
- slices may cross DVD chapter boundaries;
- identical requests are detected before creating duplicate work;
- filenames and job tags are generated by the server, not accepted as raw
  paths from the browser.

### 5. Monitor and control jobs

The queue screen shows:

- state and current pipeline stage;
- chapter/slice name and source time range;
- priority and queue position;
- frames completed / total and percentage;
- current processing rate;
- elapsed time and ETA;
- GPU memory/utilization and free disk space;
- recent log output;
- output and comparison links when completed.

Controls:

- start queued job;
- pause request;
- resume;
- cancel with confirmation;
- retry failed stage;
- move up/down or change priority;
- generate/re-generate a comparison clip;
- reveal/download output.

## Pause and resume semantics

Do not implement pause with `SIGSTOP`, Docker pause, or by freezing a process
that retains GPU memory. A frozen SeedVR2 container would keep roughly 56 GB of
VRAM and is unsafe operationally.

Pause is cooperative:

1. UI changes the job to `pause_requested`.
2. Worker finishes the current atomic restoration chunk.
3. Worker validates and atomically records that chunk.
4. Models/processes exit and release GPU memory.
5. Job becomes `paused`.
6. Resume begins at the first uncompleted chunk.

The current `pipeline_v3.sh` is resumable by major stage but SeedVR2 internally
streams multiple chunks into one output. The worker must therefore refactor a
selected range into independently durable restoration units before true UI
pause/resume is offered.

Recommended unit:

- approximately 15 seconds / 750 new source frames at 50p;
- four context frames from the previous unit;
- four warm-up frames only for the first unit;
- output only the requested new frames;
- record frame count, duration, checksum and settings for every completed
  unit.

Final assembly concatenates validated chunks and performs one sample-accurate
audio mux. A pause may consequently take up to the duration of the current
chunk's processing, approximately 18 minutes at the measured rate. The UI must
say “pausing after current chunk” rather than implying an instant pause.

## Job states

Canonical states:

- `queued`
- `preparing`
- `running`
- `pause_requested`
- `paused`
- `resuming`
- `assembling`
- `completed`
- `failed`
- `cancel_requested`
- `cancelled`

Every state transition is timestamped and appended to a job event log. On
application restart, jobs left in an active state are marked `interrupted`,
their completed artefacts are validated, and they become resumable or failed
with an explanation.

## Progress and ETA

The backend reports structured events rather than making the browser parse
human log text.

Minimum progress payload:

```json
{
  "job_id": "dvd1-title1-chapter07",
  "state": "running",
  "stage": "seedvr2_decode",
  "chunk": 3,
  "chunks_total": 8,
  "frames_done": 2250,
  "frames_total": 6000,
  "fps": 0.71,
  "elapsed_seconds": 3170,
  "eta_seconds": 5282,
  "gpu_memory_mib": 57334
}
```

Progress should be based on completed source/output frames, not console line
count. ETA uses measured rates by stage, with an exponentially weighted recent
rate and the reference benchmark as a cold-start estimate. The UI labels early
ETAs as estimates and shows the time of the last update.

Use Server-Sent Events or short polling for updates. SSE is sufficient because
commands still use normal authenticated HTTP requests.

## Data model

Use SQLite in WAL mode. It is appropriate for one user and one GPU worker while
providing transactions and restart recovery that JSON files cannot.

Core tables:

- `discs`: ISO identity, path, label, size, checksum/fingerprint, scan status;
- `titles`: disc, DVD title number, duration, streams and raw navigation data;
- `chapters`: title, number, start, end, generated label, user label, priority,
  notes and proxy state;
- `slices`: title, start, end, name, note and optional source chapters;
- `jobs`: target, settings snapshot, priority, queue position, state, timestamps,
  progress, error and output paths;
- `job_chunks`: job, sequence, source frame/time range, context, state,
  checksums and artefact paths;
- `job_events`: append-only state/progress/log events;
- `artifacts`: kind, path, media metadata, checksum and validation state.

Every job stores a complete settings snapshot. Changing future defaults must
not change the meaning of an already queued or completed job.

## Suggested HTTP API

Read endpoints:

- `GET /api/discs`
- `POST /api/discs/scan`
- `GET /api/discs/{disc_id}/titles`
- `GET /api/titles/{title_id}/chapters`
- `GET /api/titles/{title_id}/proxy`
- `GET /api/jobs`
- `GET /api/jobs/{job_id}`
- `GET /api/jobs/{job_id}/events`
- `GET /api/jobs/{job_id}/stream` (SSE)

Write endpoints:

- `PATCH /api/chapters/{chapter_id}` for name, priority and notes;
- `POST /api/slices`;
- `POST /api/jobs`;
- `POST /api/jobs/{job_id}/start`;
- `POST /api/jobs/{job_id}/pause`;
- `POST /api/jobs/{job_id}/resume`;
- `POST /api/jobs/{job_id}/cancel`;
- `PATCH /api/jobs/{job_id}/priority`;
- `POST /api/jobs/{job_id}/retry`.

All write endpoints validate current state so repeated clicks are idempotent or
return a clear conflict instead of launching duplicate containers.

## Worker architecture

Only one process owns the restoration queue and GPU lock. The web request
handler never runs SeedVR2 directly.

Recommended components:

1. Flask API and static UI.
2. SQLite database.
3. One host worker service that polls/claims queued jobs transactionally.
4. Existing pinned Docker images for media/model execution.
5. A structured event writer shared by stage wrappers.

Do not mount the unrestricted Docker socket into a remotely reachable web
container. Either run the worker as a narrowly configured host service or use a
small local-only control socket with a fixed command schema.

Worker rules:

- one GPU restoration at a time;
- source ISOs mounted/read read-only;
- no user-provided shell fragments or filesystem paths;
- stage outputs use `.partial` then atomic rename;
- validate duration, frame count, codec and colour tags before completion;
- preserve completed chunks across failure/reboot;
- capture stdout/stderr to per-job logs;
- enforce free-space thresholds before starting each stage;
- cancel gracefully at a safe boundary, with force termination as an explicit
  second action.

## Storage estimates and safeguards

At the tested quality, one 18-second job used roughly:

- 269 MB lossless deinterlaced input;
- 92 MB baseline;
- 105 MB restored video intermediate;
- 107 MB final restored output.

Actual size depends heavily on scene complexity. Before accepting a job, show
an estimate based on duration and recent jobs, plus current free space. The
worker must refuse to start if doing so would cross a configurable reserve.

Retention is explicit:

- always keep ISO and final output;
- keep baseline/comparison by default;
- keep resumable chunks until final verification;
- offer, but never automatically perform, cleanup of lossless preparation and
  model intermediates;
- show exactly how much space a proposed cleanup would recover.

## Remote access and security

The existing voting app states that it has no authentication. That is not
acceptable for a UI able to start containers or delete/cancel jobs.

Minimum deployment rules:

- bind privately, preferably through Tailscale or a private reverse proxy;
- require authentication for every page and API endpoint;
- protect writes against CSRF;
- do not expose the project root as a static directory;
- serve only registered media artefacts with HTTP Range support;
- log user actions and source address;
- rate-limit control endpoints;
- never accept arbitrary output paths or command-line arguments.

## Initial UI screens

### Library

- disc cards for DVD 1 and DVD 2;
- scan/re-scan status;
- titles sorted by duration;
- warnings for menus, duplicates and very short titles.

### Title/chapter browser

- title proxy player and timeline;
- chapter cards with thumbnail, number, duration, priority and state;
- rename/note/priority controls;
- multi-select and queue action;
- custom in/out slice controls.

### Queue

- currently running job at top;
- draggable or button-based order for queued jobs;
- priority, progress, elapsed and ETA;
- pause/resume/cancel controls with honest safe-boundary wording.

### Job detail

- source range and settings snapshot;
- stage/chunk/frame progress;
- GPU/disk metrics;
- live structured log;
- completed chunk map;
- output, baseline and comparison players/downloads;
- retry and cleanup actions.

## Implementation phases

### Phase 1: inventory only

- add reproducible environment/dependencies for ISO scanning;
- scan both ISOs and store normalized titles/chapters;
- generate thumbnails/contact strips/proxies;
- build read-only library and chapter browser;
- verify chapter times against actual playback.

### Phase 2: durable job model

- add SQLite schema/migrations;
- create slice and queue APIs;
- add single-worker GPU lock and structured events;
- run short jobs end to end from the UI;
- recover cleanly after backend/worker restart.

### Phase 3: real pause/resume

- refactor restoration into durable 750-frame units;
- validate/checksum each unit;
- cooperative pause, resume and safe cancellation;
- final chunk assembly and audio mux;
- accurate progress and ETA.

### Phase 4: review and operations

- synchronized original/restored player;
- automatic comparison generation;
- storage estimates and cleanup UI;
- authentication, private deployment and action audit;
- end-to-end tests using a short chapter and a custom slice.

## Definition of done

The first usable release is complete when:

- both ISOs show correct titles, chapters, durations and playable proxies;
- a chapter and an arbitrary slice can each be queued;
- only one GPU restoration runs at a time;
- progress, elapsed time and ETA update without parsing in the browser;
- pause finishes the current chunk, releases VRAM, and resume continues without
  recomputing completed chunks;
- restart recovery works during queued, running and paused states;
- outputs validate at the requested frame count/duration and appear in the UI;
- the application is authenticated and cannot execute arbitrary commands or
  expose arbitrary server files.
